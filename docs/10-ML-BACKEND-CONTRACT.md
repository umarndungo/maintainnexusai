# ML ↔ Backend ↔ Frontend Contract

**Status:** Draft shared contract.

## Prediction API
`POST /api/v1/ml/predict-risk`

The backend sends telemetry + asset context. The ML service does not query operational databases.

### Request
```json
{
  "equipment_id": "PUMP-001",
  "equipment_type": "PUMP",
  "station_id": "DEPOT-01",
  "timestamp": "2026-09-12T05:00:00Z",
  "features": {
    "vibration_rms": 4.2,
    "bearing_temperature": 91.5,
    "motor_current": 38.4,
    "suction_pressure": 3.1,
    "discharge_pressure": 8.4,
    "flow_rate": 412.0,
    "rpm": 1480.0,
    "running_hours": 10234.0
  },
  "asset_context": {
    "installation_date": "2020-04-15",
    "last_service_date": "2026-08-20",
    "criticality": "CRITICAL"
  }
}
```

### Response
```json
{
  "equipment_id": "PUMP-001",
  "equipment_type": "PUMP",
  "risk_score": 0.87,
  "risk_level": "HIGH",
  "prediction_horizon_hours": 24,
  "top_features": [
    "vibration_rms above recent baseline",
    "bearing_temperature trending upward"
  ],
  "model_version": "pump-baseline-1.0.0",
  "prediction_id": "PRED-001",
  "timestamp": "2026-09-12T05:00:01Z"
}
```

### Rules
- `risk_score`: 0–1.
- `risk_level`: generated by ML service; clients do not reimplement thresholds.
- `top_features`: ranked, human-readable.
- `model_version` and `prediction_id`: mandatory.
- ML predicts; it does not reschedule trucks or directly actuate equipment.

## Prediction event
`PREDICTIVE_FAILURE_RISK_DETECTED`

Carries `event_id`, `prediction_id`, asset identity/type, station, score, risk level, horizon, model version and timestamp.

## Decision output
Example:
```json
{
  "decision_id": "DEC-001",
  "prediction_id": "PRED-001",
  "decision_type": "RESCHEDULE_LOADING",
  "reason": "Critical pump risk affects three scheduled trucks; compatible alternative loading point has capacity.",
  "affected_equipment_id": "PUMP-001",
  "affected_truck_ids": ["TRUCK-104", "TRUCK-108", "TRUCK-112"],
  "target_loading_point_id": "LP-04",
  "requires_human_approval": false,
  "policy_version": "automation-policy-1.0"
}
```

## Action request
```json
{
  "action_id": "ACT-001",
  "decision_id": "DEC-001",
  "action_type": "RESCHEDULE_TRUCK",
  "truck_id": "TRUCK-104",
  "original_loading_point_id": "LP-03",
  "new_loading_point_id": "LP-04",
  "idempotency_key": "DEC-001:TRUCK-104",
  "requested_at": "2026-09-12T05:00:02Z"
}
```

## Feedback event
`OPERATIONAL_ACTION_OUTCOME`

Carries action/prediction IDs, action success, actual failure, actual delay, downtime avoided and timestamp.

## Ownership
| Artifact | Owner | Consumers |
|---|---|---|
| Feature definitions | ML | Data, Backend |
| Prediction API | ML | Backend |
| Prediction event | ML + Backend | Backend |
| Decision rules | Backend/Product | ML, Frontend |
| Action APIs | Backend | Frontend/event consumers |
| Action UI | Frontend | Operations |
| Deployment | DevOps | ML, Backend, Frontend |
| Feedback schema | ML + Backend | ML, Data, Frontend |

## Safety boundary
Automated scheduling/reassignment is a prototype target. Direct physical control of safety-critical valves/pumps is not a model-level action; any future integration requires approved interlocks, authorization and fail-safe controls.
